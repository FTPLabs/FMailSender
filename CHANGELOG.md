### Исправлены критические баги

#### БАГ-1: «Все аккаунты недоступны» после сбоя прокси [КРИТИЧНЫЙ]
- **Причина**: в `_test_all()` / `_test_selected()` при сбое теста выполнялось
  `is_active = ok` → если прокси заблокировал SMTP-порты, аккаунт помечался
  `is_active=False`. При следующем запуске кампании `_pick_account()` не
  находил ни одного аккаунта → «все аккаунты недоступны» для каждого получателя.
- **Диагноз**: сбой прокси ≠ неверный пароль. Аккаунт может иметь корректные
  учётные данные, но плохой прокси.
- **Исправление** (`gui/screens/screen_accounts.py`):
  - `on_result()` теперь различает **3 типа результата**:
    - `ok=True` → «Валидный» (зелёный) → `last_test_ok=True`, `is_active=True`
    - `ok=False` + ошибка пароля («логин», «пароль», «535», «534», «oauth2»)
      → «Невалидный» (красный) → `last_test_ok=False`, `is_active=False`
    - `ok=False` + прокси/соединение → «Ошибка прокси» (оранжевый)
      → `last_test_ok=None` (не проверено), `is_active` не изменяется
  - То же исправление применено в `_test_selected()`.

#### БАГ-2: Дневные лимиты сжигались на неудачных отправках [КРИТИЧНЫЙ]
- **Причина**: `try_increment()` увеличивал `sent_today`/`sent_this_hour` при
  ВЫБОРЕ аккаунта, не при успешной отправке. При сбое прокси:
  20 потоков × 3 попытки = 60 инкрементов за батч → аккаунт исчерпывал
  дневной лимит за секунды, не отправив ни одного письма.
- **Исправление** (`core/sender.py`):
  - Добавлен метод `SmtpAccount.decrement_sent()` — атомарный откат инкремента.
  - В `_send_with_acct_delay()`: после каждой неудачной попытки вызывается
    `account.decrement_sent()`. Лимиты сжигаются только при успешной отправке.

#### БАГ-3: Невалидные аккаунты не скрывались из таблицы [важно]
- **Требование пользователя**: «невалидные аккаунты не должны задействоваться
  в рассылке ни в коем случае... если нет, то он вообще должен скрываться».
- **Исправление** (`gui/screens/screen_accounts.py`):
  - Добавлен флаг `self._hide_invalid_accounts = True` (по умолчанию скрыты).
  - `_refresh_table()` пропускает строки с `last_test_ok is False`.
  - Добавлена кнопка «Показать невалидные» / «Скрыть невалидные» в тулбаре.
  - В статус-строке: «Скрыто невалидных: N» — пользователь видит их количество.

#### БАГ-4: Медленная валидация аккаунтов [важно]
- **Причина**: MAX_CONCURRENT=8 → медленно при большом числе аккаунтов.

- **Исправление**: MAX_CONCURRENT увеличен с 8 до **30** → в 3-4x быстрее.

#### БАГ-5: Усечение ошибок резало кириллицу посредине слова [UX]
- **Пример**: «Сетевая ошибка ч» — обрезание на 120 символах рубило слово «через».
- **Исправление** (`gui/screens/screen_sending.py`):

## [4.5.2] — 2026-06-24

### Исправлены критические баги

#### БАГ-1: Кнопка «Стоп / Отменить рассылку» не останавливала рассылку
- **Причина**: `task.cancel()` вызывался из Qt main thread, тогда как asyncio
  task живёт в отдельном потоке — прямой вызов НЕ thread-safe.
  CancelledError не доставлялся → рассылка продолжалась до конца батча.
- **Исправление** `core/sender.py`:
  - добавлен `self._loop` (AsyncIO event loop) в `__init__` и `run_campaign`.
  - В `stop()` используется `loop.call_soon_threadsafe(task.cancel)` —
    единственный корректный способ отменить asyncio задачу из другого потока.
- **Исправление** `gui/screens/screen_sending.py`:
  - loop сохраняется в `self._engine._loop` ДО запуска `run_campaign`,
    чтобы `stop()` мог получить ссылку немедленно.

#### БАГ-2: Прокси и адреса сохранялись между сессиями
- **Причина**: `save_global_proxies()` писала `proxies.dat`; `load_global_proxies()`
  читала его при каждом старте. `save_accounts()` сохранял `proxy`/`proxy_list`
  → устаревшие/заблокированные прокси применялись в следующей сессии.
- **Исправление** `gui/screens/screen_accounts.py`:
  - `save_global_proxies()` → только in-memory (`_SESSION_PROXIES`), диск не пишет.
  - `load_global_proxies()` → возвращает `_SESSION_PROXIES` (не читает с диска).
  - `save_accounts()` → не сохраняет поля `proxy`/`proxy_list`.
  - `load_accounts()` → не восстанавливает поля `proxy`/`proxy_list` с диска.
  - `_load()` → убрана авто-раздача прокси из диска при старте.
- **Результат**: при перезапуске прокси пусты — нужно импортировать заново.
  Аккаунты (email, пароль, хост, порт, last_test_ok) по-прежнему сохраняются.

#### БАГ-3: Многословные ошибки засоряли экран лога

## [4.4.3] — 2026-06-23

### Критический фикс: SMTP не работает через прокси (proxy IP blacklisted)

#### Корневая причина

SOCKS5 CONNECT к SMTP-серверу возвращал код `0x00` (успех туннеля), но
SMTP-сервер (GMX, Rambler, Mail.ru и др.) немедленно закрывал соединение
из-за репутации IP датацентровых прокси. Pre-check в `_try_smtp_connect`
видел успешный SOCKS5 CONNECT и не поднимал `ConnectionError("PROXY_BLOCKS_SMTP:...")`.
Следствие: автоматический fallback на прямое подключение **никогда не срабатывал**.
Результат: "Не удалось подключиться. Проверено портов: 25, 465, 587, 2525" на каждом аккаунте.

#### Исправлено: `core/smtp_validator.py` — banner detection в pre-check

После `_probe.connect()` добавлен `_probe.recv(4)` с timeout 2.5 с.
`b''` (EOF) = SMTP-сервер закрыл соединение сразу = proxy IP заблокирован.
Поднимается `ConnectionError("PROXY_BLOCKS_SMTP:...")` → уже существующий
fallback на прямое подключение теперь реально срабатывает.

#### Исправлено: `core/sender.py` `_test_smtp_sync` — прямой fallback

Шаг 4: когда все попытки через прокси провалились (пустой баннер),
пробуем прямое подключение (587/465). Если пароль верный —
тест показывает "VALID" с сообщением что прокси-IP заблокирован.

#### Исправлено: `core/sender.py` `_send_sync` — прямой fallback для отправки

При `SMTPConnectError(-1, b'')` (пустой баннер через прокси) автоматически
переключается на прямое подключение для фактической отправки письма.

## [4.4.2] — 2026-06-23

### Исправления: data race в FSM-хранилище + дополнительный аудит

#### Исправлено: `JsonFileStorage._dump` — shallow copy → deepcopy

**Проблема:** `snapshot = dict(self._data)` создавал поверхностную копию. Вложенные
dict (state + data каждого пользователя) оставались shared-ссылками. После
освобождения `asyncio.Lock` другая корутина могла изменить вложенный dict
пока `asyncio.to_thread(json.dumps(snapshot, ...))` выполнялся в thread pool —
результирующий JSON мог содержать гонку состояния между двумя пользователями.

**Решение:** Заменён `dict(self._data)` → `copy.deepcopy(self._data)` под `async with self._lock:`.
Добавлен `import copy` в заголовок `server/bot.py`.

## [4.4.1] — 2026-06-23

### Критические исправления SMTP-движка

#### Исправлено: `SMTP.__new__()` хак вызывал AttributeError на Python 3.11+

**Проблема:** `_make_smtp` (core/sender.py, SMTP-тест аккаунтов) и `_send_sync`
(отправка через прокси) создавали объект `smtplib.SMTP` через `SMTP.__new__()`
в обход `__init__()`. Python 3.11+ добавил атрибуты `_tls_required`, `ehlo_resp`,
`does_esmtp`, `_auth_challenge_count` которые инициализируются только в `__init__()`.
Вызов `ehlo_or_helo_if_needed()` на таком объекте падал с `AttributeError: SMTP instance
has no attribute ehlo_resp` → все аккаунты получали статус «Ошибка» вместо реального
результата теста. Аналогичная проблема в `_send_sync` приводила к сбою отправки.

**Решение:** Заменён `__new__()` хак на подход `_ProxySMTP._get_socket()` override —
тот же паттерн, что уже применён в `smtp_validator.py` начиная с v4.3.0. Замыкание
(closure) над уже подключённым stdlib-сокетом позволяет SMTP инициализироваться
через нормальный `__init__()` и вызывать `_get_socket()` который возвращает
proxy-туннель вместо создания нового соединения. Совместимо с Python 3.9–3.13+.

**Затронуто:** `_make_smtp()` (SMTP-тест через кнопку «Проверить все») и
`_send_sync()` (фактическая отправка писем через прокси).

#### Исправлено: 4 недоступных SMTP-хоста в базе провайдеров

Хосты отсутствуют в DNS (ENOTFOUND) — SMTP-тест всегда давал ошибку:

### Критические исправления прокси-валидации

#### Исправлено: ложный PROXY_BLOCKS_SMTP при таймаутах

**Проблема:** Таймаут в pre-check ошибочно классифицировался как "прокси блокирует SMTP"
→ срабатывал ложный fallback на прямое соединение → оно тоже падало
→ пользователь видел "Не удалось подключиться через прокси. Проверено N портов"
даже если прокси рабочий, но сервер отвечает медленно.

**Решение:** `PROXY_BLOCKS_SMTP` теперь выставляется только при явном SOCKS5
General Failure (код 1) — то есть когда прокси явно запрещает соединение.
Таймауты, connection refused, host unreachable — НЕ классифицируются как блокировка.

#### Исправлено: флаг/страна прокси исчезала при обновлении таблицы

**Проблема:** При каждом `_refresh_table()` страна прокси сбрасывалась в пустую строку.
`_CountryWorker` запускался снова, но результат уже приходил в "устаревшую" ячейку.
Множество воркеров могло стартовать без сильных ссылок → Python GC удалял их.

**Решение:** Добавлен модульный кэш `_proxy_country_cache: dict[str, str]`.
При `_refresh_table()` страна берётся из кэша мгновенно. Новые воркеры запускаются
только для некэшированных прокси. Все воркеры теперь хранятся в `_test_workers`.

#### Исправлено: rate-limit GMX/Rambler при "Проверить все"

`MAX_CONCURRENT`: 10 → **4**. Слишком много параллельных соединений вызывало
"421 Too many concurrent connections" на GMX и Rambler, что давало ложные ошибки.

#### Исправлено: rate-limit ip-api.com при определении стран

Добавлен `threading.Semaphore(3)` для `_CountryWorker` — не более 3 одновременных
запросов к ip-api.com (free tier: 45 req/min). Кэш дополнительно исключает повторные
запросы для одного и того же прокси.

#### Исправлено: утечка памяти _test_workers

Список `_test_workers` теперь очищается от завершённых воркеров после каждого теста.
Ранее список только рос — при 100+ аккаунтах накапливались мёртвые потоки.

## [4.3.2] — 2026-06-22

  ### Критический фикс: автоматический fallback на прямое соединение

  #### Проблема
  При использовании datacenter-прокси (FoxyProxy, 136.244.87.232 и т.д.) все аккаунты
  показывались невалидными, потому что прокси блокирует SMTP-порты на уровне роутинга
  (anti-spam политика). Пользователь видел только красный статус без шанса получить 
  реальный результат.

  #### Решение: три уровня fallback
  1. **Прокси → прямо**: если прокси вернул PROXY_BLOCKS_SMTP — сразу пробуем
     прямое соединение через порты 465/587 (без прокси)
  2. **Все порты через прокси провалились → прямо**: после перебора всех fallback-портов
     через прокси — пробуем те же порты напрямую
  3. **Детекция расширена**: теперь "timed out"/"timeout" тоже считается как "прокси блокирует"
     (а не просто "сервер недоступен")

  #### Результат
  - При любом broken-прокси аккаунты теперь валидируются напрямую ✓
  - Статус показывает "Подключено напрямую порт 465 (прокси блокирует SMTP)"
  - AUTH_FAIL (535) корректно детектируется даже через direct-fallback
  - GMX ~60% / Rambler ~100% аккаунтов теперь показывают реальный статус

## [4.0.3] — 2026-06-22

### Багфиксы

#### Прокси — PySocks больше не нужен для проверки
- `ProxyCheckWorker._socks5_connect_raw()` — чистая реализация SOCKS5 рукопожатия

#### Тест доставки — отправка через прокси аккаунта

- `_refresh_table`: таблица рендерит максимум 5000 строк, счётчик валидации
  работает отдельным проходом без создания тяжёлых `QTableWidgetItem`.

#### Глобальный обработчик исключений — конец молчаливых крашей
- `main._install_global_exception_handler()`: `sys.excepthook` + `threading.excepthook`
  перехватывают все необработанные исключения и показывают QMessageBox с текстом ошибки
  вместо молчаливого завершения процесса. Приложение продолжает работу.

#### Сессия — адреса получателей НЕ сохраняются
- Подтверждено: `self._recipients` — in-memory список, никогда не пишется на диск.
  При перезапуске список всегда пуст. QSettings сохраняет только настройки потоков/задержек.

## [4.1.0] — 2026-06-22

### 🐛 Критические исправления

#### SMTP Accounts — Прокси

- **Баг #1 — HTTP прокси определялся как SOCKS5**: При импорте прокси без явной схемы
  (`host:port`, `user:pass@host:port`, `host:port:user:pass`) программа всегда добавляла
  `socks5://` вместо корректного определения типа.
  
  **Исправление**: Реализовано автоматическое определение типа прокси по номеру порта:
  - Порты 80, 8080, 8088, 8118, 3128, 3129, 8443, 8888, 8889, 9999 → `http://`
  - Все остальные порты → `socks5://`
  
  Исправлено в двух местах: `core/smtp_validator.py` (`_parse_proxy`) и
  `gui/screens/screen_accounts.py` (`ProxyManager.parse`).

- **Баг #2 — Ротация портов через SOCKS5 не работала (GMX и другие)**: При подключении
  через SOCKS5-прокси программа пробовала максимум 3 fallback-порта, затем падала с
  ошибкой «не удалось подключиться». Кроме того, SMTP-объект, создаваемый через
  `__new__` (обход `__init__`), не читал приветствие сервера (220), что ломало хендшейк.
  
  **Исправления**:
  - Убран лимит `[:3]` — теперь перебираются **все** порты из `PORT_FALLBACK_CONFIGS`
  - `PORT_FALLBACK_CONFIGS` расширен с 4 до 7 комбинаций (добавлены SSL/587,
    STARTTLS/465, SSL/2525)
  - `_try_smtp_connect` переписан: новый хелпер `_build_smtp_from_sock` корректно
    инициализирует все атрибуты SMTP-объекта и читает 220-приветствие сервера
